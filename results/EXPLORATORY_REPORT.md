# Jordan EHR Dataset — Exploratory Report

Generated by [Create_codes/explore_data.py](../Create_codes/explore_data.py). Read-only exploration — no
model has been built. Raw data lives in `Dataset/` (left untouched); this report, summary tables and
figures are in `Create_results/` and `Create_figures/` as requested.

## 0. Folder / file inventory

The dataset is **not** a single table — it's ~90 separate CSV/XLSX exports across 5 categories:

| Folder | Contents |
|---|---|
| `Dataset/Sex_birth/` | `date of birth.csv`, `females patients.csv`, `males patients.csv` — demographic backbone |
| `Dataset/Diagnosis/` | `DIAGNOSIS Direct.csv`, `DIAGNOSIS wide.csv` (patient-level problem lists) + 3 reference vocabulary files |
| `Dataset/Medications/` | `M1.csv` … `M30.csv` — 30 batch exports of one dispensing table |
| `Dataset/Vitals/` | `vitals BP.csv`, `vitals height.csv`, `vitals pulse.csv`, `vitals wt kg.csv` |
| `Dataset/lab_tests/` | 53 files (csv + 2 xlsx) covering 33 distinct analytes, several split into `11`/`22`/`33` or `1 D`/`2 D` batches |

There is no separate "raw test file" beyond `Example_transformer_model/` (a prior baseline/example you
confirmed is out of scope for this exploration).

## 1. Rows and patients

- **Total distinct patients: 382,537** (union of `date of birth.csv` + `females/males patients.csv`;
  these three files are perfectly consistent — every patient has exactly one DOB row and exactly one sex
  label, no overlap between the male/female id sets).
- Total raw rows across all files: **~26.4 million** (20.78M lab results + 2.57M medication dispenses +
  1.74M vitals readings + 512K diagnosis rows + 765K demographic rows).
- Row counts ≠ patient counts anywhere except Sex_birth — every other category is a long/event table with
  multiple rows per patient.

## 2. Columns and their meaning (best inference from content)

**Sex_birth**
- `PATIENT_ID` — patient key used consistently in Diagnosis/Medications/Vitals/Sex_birth (note: lab_tests
  uses `PatientID`, no underscore — same identifier space, just inconsistent naming across exports).
- `DATE_OF_BIRTH` — one row per patient, range 1907–2024 (1 unparseable row).
- `SEX` — split across two separate files instead of one column; disjoint, no patient in both.

**Diagnosis**
- `PROBLEM_ID` — unique key per problem-list entry.
- `CODE_NUMBER` — looks like ICD-9-CM style codes (e.g. `401.9`, `250`).
- `DIAGNOSIS` — free-text label matching the code (e.g. `HYPERTENSION NOS`).
- `DATE_ENTERED` — day-resolution date the problem was entered, range 2018-01-01 to 2022-06-30.
- `DIAGNOSIS Direct.csv` vs `DIAGNOSIS wide.csv`: **every row of Direct also appears in wide** (238,529
  shared pairs), and wide has 24,989 additional rows on top — wide is effectively a superset export, not a
  different dataset. Recommend using `wide` alone.
- `DIAGNOSIS TYPES TOTAL 8600.csv`, `diagnosis 760.csv`, `diagnosis 899.csv` — **not patient-level data**,
  just reference vocabulary lists of diagnosis label strings (the 760/899 lists are shorter and look like
  curated diabetes-relevant subsets).

**Medications**
- `PATIENT_ID`, `DISPENSED_DATE` (day resolution, 2017-03-19 to 2023-08-31), `GENERIC_NAME` (drug name +
  strength, only **21 distinct values** — this looks like a diabetes-medication-only extract, not a full
  pharmacy record), `QTY` (units dispensed), `DAYS_SUPPLY` (how many days the dispensed quantity should last).
- **Schema is inconsistent across the 30 batch files**: `M22`–`M30` (9 files) are missing `DAYS_SUPPLY`
  entirely; `M10` has one extra column `R` (always `TRUE`, meaning undocumented — possibly a refill flag).
  Any days-supply-based feature will only be computable for 21 of the 30 batches.

**Vitals**
- `vitals BP.csv`: `PATIENT_ID`, `NAME` (constant "BLOOD PRESSURE"), `RATE` — a **string** `"systolic/diastolic"`
  (e.g. `"130/74"`), 100% of rows follow this pattern and need splitting into two numeric columns.
- `vitals pulse.csv`: `PATIENT_ID`, `NAME`, `RATE` (numeric beats/min).
- `vitals height.csv`: `PATIENT_ID`, `NAME`, `height inch`, `height cm` (redundant unit pair).
- `vitals wt kg.csv`: `PATIENT_ID`, `NAME`, `wt pound`, an unnamed blank column, `wt kg` (redundant unit pair + a stray empty column from the source export).
- **None of the 4 vitals files has any date or timestamp column** (see §4).

**Lab tests** (uniform schema across all 33 analytes)
- `PatientID`, `LAB_DATA_CHEMISTRY_RESULTS` (numeric result), `DATE_TIME_SPECIMEN_TAKEN` (full
  date+time), `LabTestName` (analyte code, e.g. `HbA1C`, `FBS`, `CRT`, `NA` for sodium).
- The `11`/`22`/`33` and `1 D`/`2 D` suffixes are **batch-split exports of the same analyte** (identical
  columns, identical `LabTestName` value, non-overlapping row ranges) — not different meanings. Combine
  same-analyte files before use.
- Gotcha found and fixed during exploration: pandas' default missing-value list treats the literal string
  `"NA"` (the sodium analyte code) as a null — naive loading silently drops sodium's test-name label.

## 3. Sparsity / missingness

Within-file missingness is negligible everywhere it matters:
- Lab tests: 0% missing result values across all 33 analytes; missing/unparseable dates are ≤0.9% per file
  (mostly 0%).
- Medications, Diagnosis, Sex_birth: 0% missing on their core fields.

The real sparsity is **across categories**, i.e. how many of the 382,537 patients actually have each kind
of data (see `Create_figures/cross_category_coverage.png`):

| Category | Patients | % of total |
|---|---:|---:|
| Sex / DOB | 382,537 | 100.0% |
| Labs (any analyte) | 382,536 | 100.0% |
| **HbA1c specifically** | 382,472 | 100.0% |
| Diagnosis | 153,097 | 40.0% |
| Medications | 102,465 | 26.8% |
| Vitals (any) | 75,569 | 19.8% |
| **All four** (dx + meds + vitals + labs) | 19,130 | 5.0% |

So this is fundamentally a **labs-centric** export — essentially every patient has lab data (and HbA1c
specifically), but only a minority have diagnosis codes, medication dispenses, or vitals on file. Only 5%
of patients have complete coverage across all four non-demographic categories.

## 4. HbA1c value range

- 1,139,747 raw HbA1c measurements across `HBA1C 11.csv` + `HBA1C 22.csv`, covering 382,472 patients
  (100% of the cohort).
- **Raw values are corrupted at the extreme tail**: max = 3,438,171,009 (a single garbage row, patient
  2593528, 2018-06-20) drags the naive mean to 3,023 — do not use raw mean/std.
- 109 rows (<0.01%) exceed 20%, 7,526 rows are below 3% — implausible for an HbA1c% and should be treated
  as data-entry errors / cleaned before any modeling.
- **Restricting to a clinically plausible [2, 20]% range** (99.33% of all rows, n=1,132,129):
  - min 2.00, max 20.00, **mean 6.84, median 6.10, std 1.97**
  - p5 = 4.8, p25 = 5.4, p75 = 7.8, p95 = 10.9
  - Median sits above the normal cutoff (5.7%), consistent with a diabetes-focused cohort — matches the
    medication list being diabetes-drug-only and the curated diagnosis vocab files.
- Date range of measurements: 2011-01-12 to 2025-05-26.
- See `Create_figures/hba1c_distribution.png`.

## 5. Temporal structure — honest assessment

**Yes, more than one time point per patient exists for labs, and visits CAN be ordered — but only for
about half the cohort, and only for labs/meds/diagnosis, not vitals.**

- Of the 382,472 patients with any HbA1c, **203,053 (53.1%) have 2 or more dated measurements** — a real
  basis for an irregularly-spaced longitudinal sequence. The other 179,399 (46.9%) have only a single
  snapshot, so a sequence model needs to gracefully handle length-1 "sequences" or exclude them.
- Spacing between consecutive HbA1c draws for the same patient: median 182 days, 5th pct 28 days, 95th
  pct 952 days — roughly consistent with quarterly-to-annual clinical monitoring (see the ~90-day mode in
  `Create_figures/hba1c_gap_days.png`), with a long tail of sparse/irregular follow-up.
- **Lab panels can be reconstructed**: a large share of HbA1c draws share the exact same
  `(PatientID, DATE_TIME_SPECIMEN_TAKEN)` timestamp as other analytes — 23.5% match FBS, 26.4% match
  Creatinine, 18.9% match Hemoglobin. `(PatientID, DATE_TIME_SPECIMEN_TAKEN)` is therefore a legitimate
  join key to assemble a multi-analyte "visit" row, not just a single-value time series.
- **Medications** (`DISPENSED_DATE`) and **Diagnosis** (`DATE_ENTERED`) only have day-resolution dates —
  orderable, and joinable to lab visits by nearest date, but not to the minute.
- **Vitals have no date or timestamp field at all**, in any of the 4 files. Row order is contiguous by
  patient within each file, but there is no evidence — and no way to verify from the data alone — that
  row order within a patient's block is chronological. **Vitals cannot be honestly sequenced with this
  export.** Options, in order of preference:
  1. Treat vitals as **static/aggregate** features only (e.g. last recorded weight, mean pulse, count of
     BP readings) rather than as a time series — safest and defensible with the current data.
  2. If whoever ran the extraction can confirm the source query was ordered chronologically, row order
     could be used as a weak proxy — but this needs to be verified externally, not assumed.
  3. Request a re-extraction that includes the missing date/timestamp column if vitals dynamics over time
     are actually needed for the model.

**Bottom line:** a genuine per-patient sequence model is defensible for **labs** (HbA1c plus panel-mates),
doable at day-resolution for **diagnoses/medications**, but **not honestly possible for vitals** as
currently exported.

## 6. Data quality issues to resolve before modeling (not fixed yet — exploration only)

1. HbA1c (and likely other analytes) contain extreme outlier values that need clipping/removal.
2. Medication batch files have inconsistent schemas (`DAYS_SUPPLY` missing in 9/30 files).
3. Vitals `wt kg.csv` has a stray unnamed empty column.
4. Vitals BP `RATE` is a systolic/diastolic string that needs splitting.
5. Patient ID column is named `PATIENT_ID` in every category except lab_tests (`PatientID`) — trivial but
   needs normalizing when joining.
6. `DIAGNOSIS Direct.csv` is a subset of `DIAGNOSIS wide.csv` — only one is needed.
